# 存档桥与确定性回放（契约草案 v0）

> 适用范围：`games/fe8-remake`。这份文档只定**游戏侧**职责；存储、配额、淘汰归平台（插件/后台）。

## 1. 游戏侧只暴露三个动作

```js
snapshot()      // -> { schema, gameVersion, payload }  纯函数，不改游戏状态
restore(snap)   // -> { ok, reason? }                   校验后注入；失败必须带明确原因
meta()          // -> { gameVersion, chapter, turn, playtimeMs }  列表页轻量信息
```

游戏侧**不做**：落盘、配额、淘汰、跨设备同步、UI 列表。

`snapshot()` 的 `payload` 必须包含：单位全量状态、地图/地形状态、章节进度、回合数、
**PRNG 状态**、**待处理输入队列长度**。少了 PRNG 与输入队列，读档后每帧分叉，战斗结果与原版不一致。

## 2. 存档池策略（游戏侧实现，已落地 `src/save/save-pool.js`）

| 池 | 上限 | 说明 |
| --- | --- | --- |
| `manual` | 无 | 玩家主动存，永不自动删除 |
| `auto` | 20 | 每 5 分钟一次；满 20 份时**淘汰最旧的一份自动存档** |
| `auto` + `reason:'close'` | 同上 | 关闭游戏时的那次存档进**自动池**，不混进手动池 |

其他硬规则（均已实现并有测试）：

- **单写者队列**：任何时刻只有一个写事务，5 分钟定时器与"关闭"撞车也不会写坏索引。
- **读档先校验 checksum**：坏档返回 `CORRUPT`，**不得覆盖**任何好档。
- **版本不兼容显式报错**：`VERSION_MISMATCH`，消息里带旧版本与当前版本，禁止静默失败。
- 元信息最小集：`{slot, pool, reason, createdAt, gameVersion, bytes, checksum, schema}`。

存储介质用 **IndexedDB**（不是 localStorage）：单份存档 20–80 KB，20 份 2 MB 起，
localStorage 全域 5 MB 且同步阻塞，会卡帧。

## 3. 确定性回放的三条硬约束

要能"同一输入脚本 → 同一结果"，必须同时满足：

1. **固定帧步进**：逻辑严格 60 Hz 定步，不读 `requestAnimationFrame` 的时间差；渲染只做插值，不推进状态。
2. **种子化 RNG**：全引擎只有一颗 PRNG（xorshift128），种子进存档快照，禁止 `Math.random()`。
3. **输入按帧对齐**：按键脚本 `[{frame: 12, keys: ['A']}, ...]` 喂进同一入口，回放不经过真实键盘事件。

满足后可以给出两类证据：
- 自证：「同脚本两次运行 → 状态哈希相同」
- 对外：「第 N 帧状态哈希」序列，供对拍

**做不到的**：与原版 ROM 逐帧**像素**哈希一致。原因见下。

## 4. 为什么"逐帧像素一致"和"重写引擎"互斥

逐帧画面哈希与原 ROM 相同，只有执行 ROM 原始 ARM 指令（WASM 模拟器 + 外壳）才能做到。
自己写引擎时，字体光栅化、卷屏亚像素插值、随机数序列、AI 决策顺序都会不同，1800 帧内必然分叉。
这是原理性差异，不是工程投入能补的。因此验收判据必须二选一：

- 路线 R（跑原 ROM）：判据可设逐帧像素一致；但"用游戏内资源转成网页游戏"不成立。
- 路线 W（重写引擎）：判据改为**逻辑状态逐帧相等 + 静态截图人工对照 + 数值表 diff 为空**。
