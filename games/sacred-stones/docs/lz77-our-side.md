# LZ77 清单对账：我们这一侧的口径与实测

> 清单：`extract/lz77-pointers-4451.tsv`（4,451 行）
> 生成：`node scripts/export-block-list.mjs`
> 比较：`node scripts/compare-block-lists.mjs <A.tsv> <B.tsv> --out <dir>`

## 一、四桶结果（A = 我们 4,451，B = 逆向 4,463）

```
shared 4451   onlyA 0   onlyB 12   fieldMismatch 0
```

- **onlyB 12 块全部 `dlen < 32`**（dlen 分别是 1、9、10、17、19 字节）。这类长度不可能是一块图块/字库素材，属于"指针指向的小数据片段被当成压缩块"。我们的一道闸门是 `dlen >= 32`，正好把它们挡在外面。
- **`fieldMismatch = 0`**：重叠的 4,451 块上 `dlen`/`clen` 逐字相同 ⇒ **两套解码器已经互证**，剩下的差全部是"扫不扫得到"，不是"解不解得对"。

## 二、三道闸门与两条实测修正

| 闸门 | 取值 | 依据 |
| --- | --- | --- |
| 指针来源 | 只认被 32 位字 `0x08xxxxxx` 指向的偏移 | 资产表口径；纯扫描会引入大量未引用假阳性 |
| `dlen` 下限 | `>= 32` | 挡小片段（实测正是 onlyB 的那 12 块） |
| `dlen` 上限 | `<= 0x100000` | 假块头常声明十几 MB |
| 压缩比 | `dlen <= 16 * clen` | **实测改过两次**，见下 |
| `dlen` 语义 | 解压后**精确**长度 | 头部声明与产出必须逐字节相等 |
| 目标偏移对齐 | **不要求** | **实测推翻**，见下 |

### 修正一：压缩比上限从 8 改到 16

与逆向清单做集合差后，有 **25 块**落在 `dlen/clen = 8.05~8.40`。抽查特征：`dlen` 与头部声明**完全一致**、能精确解出、能被指针引用、内容是高重复数据（整块同色图块那类）。

上限的本意是挡"随机字节冒充块头"（那类会声明十几 MB、压缩比高达几十上百），不是挡"压得太好"。所以放到 16 仍然挡得住假阳性，但不再误杀真块。

### 修正二：取消"目标偏移 4 字节对齐"

原来要求 `offset % 4 == 0`，理由是"ARM 数据都对齐"。实测反例：

```
偏移 0xA1317E（%4 == 2）
被 0x07B1C8 处的一个字 0x08A1317E 引用
头字节 0x14 → LZ77，dlen = 256，能精确解出 256 字节
```

GBA BIOS 的 LZ77 解压对**目标偏移**没有对齐要求；对齐要求只属于"指针字本身落在 4 字节边界"，而按 `p += 4` 扫描已天然满足。把这两件事混成一条闸门，就会**静默漏掉真块**。

## 三、两条方法论

1. **数字必须带着"哪个脚本 + 哪个 sha256 + 哪套判据"一起出现**。清单头注里写了 `rom_sha256` / `generator_sha256` / `decoder_sha256` / 每条闸门的取值，缺一样别人无法复算。
2. **闸门引用谓词原文，不引用名字**。本轮两次踩坑都是"名字被自由解释"：
   - `clen > 8*dlen` 是恒假条件（实测 0 条），真正的排除条件是 `dlen > 8*clen`；
   - 我自己凭印象加的 `clen >= 32` 根本不在任何一侧的口径里。

## 四、仍然成立的边界

这套清单是**资产表的候选集**，不是"这些块都是素材"。哪块是图、哪块是字库，由 VRAM oracle（`scripts/vram-oracle.mjs`）和合成器逐像素验证决定，不由块数决定。
