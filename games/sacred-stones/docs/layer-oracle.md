# 图层 oracle：用模拟器当参照

一句话：**让模拟器只画一层，我自己拼同一层，逐像素比。** 这条路上不需要任何人肉眼判断。

## 为什么不能直接比整屏

`framebuffer` 是 **4 个 BG + OBJ + 窗口 + 颜色特效**压平后的结果。拿"我拼的 BG0"去比整屏，
所有被精灵和其它层占住的像素都会算成差异——于是你会拿着一堆"我明明画对了"的红块
去查合成器，查一整天也查不出问题，因为问题不在合成器。

## 做法（`scripts/layer-oracle.mjs`）

1. 跑到目标帧（`--frames`，默认 900），一次性拷出 `vram` / `palette` / 相关寄存器；
2. 把 `DISPCNT` 收成**只开这一层**，`BLDCNT` 置 0，重渲染 160 行 → 得到"硬件渲染的纯单层"；
3. 用同一份内存快照，按 `src/extract/bg-render.js` 自己合成同一层；
4. `compare-frame.mjs` 逐像素比。

每一层都能单独验，**差异出现在哪层就说明哪层错**——分层是白送的。

## 三条必须先处理的坑（都实际踩过）

### ① 帧末读到的 DISPCNT 不可信

游戏在 VBlank 里改寄存器。帧末读出来的值可能是"下一次设置前的中间状态"。

本项目的实例：某一版代码按"寄存器序号"读（`mmio[0]`），把 `DISPCNT` 读成 `0x0040`，
据此判断"四个 BG 全关、画面只能是背景色"，然后拿一张全黑的图与另一张全黑的图比较，
**报出 diff = 0**。差一点就把它当成功。

后来发现 `mmioRegisters` 是 **`Uint8Array`（1024 字节，按字节寻址）**，
`DISPCNT` 在 byte 0..1（小端），`BG0CNT` 在 byte 0x08，`BG0HOFS` 在 0x10，`BLDCNT` 在 0x50。
按字节读 `0x1e40` 才对得上"BG1/2/3 + OBJ 全开"。

### ② 空的参照帧不构成判据

同一个 `DISPCNT=0x1e40` 里 **BG0 根本没开**。第一次跑 `--bg 0` 得到两张全黑图、
diff = 0，看起来"完美通过"。

所以脚本现在：**先渲染、数颜色**，少于 8 种颜色就判 `skip-blank` 并说明原因，
退出码 3（"没有可用的判据"与"判据通过"必须是两个结果）。

### ③ 颜色展开规则不同，会把每个像素都改一点

模拟器把 5 位色按 `v << 3` 展开，我按 `(v << 3) | (v >> 2)` 展开：`v=31` 时相差 7。
第一次比对报 6,241 个像素不同、`maxChannelDelta 248`，看着像合成器错了。

正确做法**不是把容差放大到 7**（那会连真实错误一起掩盖），而是两边都回到 5 位域比：
`compareFrames(..., {quantizeBits: 3})`，同一颜色量化后差异为 0。

## 实测结果（真卡带，帧 900，13,983,266 B 解压数据）

```
DISPCNT = 0x1e40（mode 0，BG1/2/3 + OBJ 开，BG0 关）
BLDCNT  = 0x0c42（有特效，所以参照帧必须先清零）
BG1     → skip-blank（隔离后只有 1 种颜色，空层不算判据）
BG2     → match：38,400 像素全等，79 种颜色
BG3     → match：38,400 像素全等，15 种颜色
```

产物：`.botharness/layer-oracle/bg{2,3}-{oracle,mine}.png` 与 `summary.json`
（`summary.json` 里记了 `frames`、五个寄存器的原值、`vram`/`palette` 的 sha256）。
**帧号是这些数字的一部分**——丢了以后没法判断"这个结论还成不成立"。

## 一个坑本身是 bug：地址算了两遍

第一版 4bpp 取像素时把"字节地址"和"像素序号"各除了一次 2：

```js
readPixelIndex(vram, tileAddr + Math.floor(pixelOffset / 2), ...)  // 内部又 offset >> 1
```

结果整层全透明，看起来像"图块不在 VRAM 里"。修法是只算一次：低半字节在左，
`pixelOffset & 1` 决定取低还是取高半字节。

## 第二轮：颜色特效（BLDCNT / BLDALPHA / BLDY）

第一轮把 `BLDCNT` 清零，等于把"半透明、淡入淡出、亮度渐变"整段功能移出覆盖范围——
而本作的菜单、转场、被选中单位的闪烁几乎全靠这几个特效。所以第二轮：

```
--round 2                       BLDCNT 保留原值，比"混合后像素"
--target self                   把本层设成第一目标（否则原帧常常只指向 BG1，等于没测）
--effect alpha|brighten|darken  覆盖特效模式
--blend-domain 8bit|5bit        混合算式在哪个位宽里算
```

**必须先 `--target self`**：帧 900 的 `BLDCNT = 0x0c42` 只把 BG1 列为第一目标，
直接拿 BG2 跑第二轮会"相符"，但那时特效根本没触发——这是空判据。

### 位域的第 13 位（踩过的坑）

`BLDCNT` 的第一目标在 bit0..5，**第二目标在 bit8..13**，第二目标里的 BD 是 bit13。
我一开始按"第二目标 BD = bit5"写，那一版硬件**完全不混合**（只有第一目标、没有第二目标时
不做任何混合，不是"和黑色混"），而我算出"整体暗一半"，于是 6,241 个像素全红，
看起来完全像我的混合公式错了。改到 bit13 后立刻相符。

### 结果（真卡带，帧 900）

| 层 | ALPHA | BRIGHTEN | DARKEN |
|----|-------|----------|--------|
| BG2 | 全等 | 全等 | 全等（8bit 口径） |
| BG3 | 全等 | 全等 | 全等（8bit 口径） |

### 两种混合口径，差在哪

`@gba-kit` 的混合是**在 8 位域**做的，而且它的 5→8 展开是 `v << 3`（不复制低位）。
真机按 GBATEK 是**在 15 位域**算。两种都跑一遍：

- ALPHA、BRIGHTEN：两种口径逐像素一致；
- DARKEN：5 位域与 8 位域最多差 **1 个 5 位级**（8 位域上 9/255），影响 5,075/38,400 个像素（13%）。

这是**口径差，不是 bug**：`(c*8)>>4` 在 c 与 c<<3 上取整位置不同。
发货代码用真机口径（`blendDomain: '5bit'`），跑 oracle 时用 `8bit` 才能和这个模拟器对上。
`docs/frame-compare.md` 里那条"量化是比对口径，不是产品口径"也同样适用于这里。

## 这条 oracle 证明什么、不证明什么

- **证明**：「我的合成器 = 这个模拟器的渲染器」。合成器对、地图解析对、
  半字节顺序对，三者错一个就红。
- **不证明**：这个模拟器 = 真机 = 原版视觉。所以它能把人类截图从"唯一判据"
  降级成"最终验收抽样"，但**不能取消**截图——两层抓的失败集合不同。
  如果哪天两边结论打架，那是本项目最有价值的一次发现，不是噪声。
