# 素材格式：已经证实的与还没证实的

这份文件只写**有实测背书**的结论。没有证据的猜测留在下面「未证实」一节，
不要当成事实引用。

## 一、卡带

| 项 | 值 |
| --- | --- |
| sha256 | 见 `src/rom-identity.js` 的 `SUPPORTED_CART_SHA256`（唯一来源，别处不要写字面量） |
| 大小 | 16,777,216 B（16 MiB） |
| 头 | `FIREEMBLEM8` / 游戏码 `BE8J` / 入口 `0x08000000` |
| 存档介质 | SRAM，32 KiB（`0x577378` 处 `SRAM_F_V103`；内核自检同样报 `SRAM_F_V103`） |
| 汉化判断 | **看文本/字库区，不能看表头**。表头校验和是 PASS 的（`sum(0xA0..0xBC)=1296`，`-(1296+0x19)&0xFF=0xD7`，`0xBD` 处也是 `0xD7`） |

## 二、压缩格式（已证实）

GBA BIOS 压缩格式的头部：`type(1) | dlen(3, 小端) | payload`，`type` 高 4 位
是格式号：`0x10` LZ77、`0x20` Huffman、`0x30` RLE。低 4 位保留、按 0 处理。

两条踩过的坑，都是"看起来实现对了、其实全错"的那种：

1. **LZ77 的标志位 1 = 压缩块、0 = 字面量**（不是反过来）。写反之后，真实块
   全部解成乱码判死，而随机字节反而"解得通"——因为全是字面量、靠 dlen 截断
   "成功"。同一份卡带两种语义对跑的判据：
   ```
   oneIsCompressed=true   候选 6557  通过 4463  压缩比中位数 2.64
   oneIsCompressed=false  候选 6557  通过   44  压缩比中位数 0.44（倒挂，不可能）
   ```
2. **Huffman 的位流是"字节内高位在前、按字节顺序"**，拼装必须大端
   `(b0<<24)|(b1<<16)|(b2<<8)|b3`；取位下标是"还剩几位"`available` 本身，
   不是 `31 - available`（那样每次都在取低位，所有符号走同一叶子、输出全 0）。

### 指针枚举 vs 纯扫描

`0x08xxxxxx` 形式的 32 位指针指向卡带内偏移。枚举到的指针里有 47,233 个落在
ROM 范围内，其中约 5,447 处的第一个字节高 4 位是 `0x1/0x2/0x3`（像压缩头）。
用严格校验 + 压缩比上限（LZ77 ≤ 8、Huffman ≤ 4、RLE ≤ 2）+ 4 字节对齐 +
`32 ≤ clen ≤ 0x100000` 筛下来：**LZ77 解出 4,425 块，clen 6,009,879，
dlen 13,983,266（压缩比 2.33）**。Huffman 与 RLE 目前解出 0 块，按"不给数"处理。

> 压缩比上限不是洁癖：没有它时 RLE 会"成功"解出 51 块、合计 254 MB
> （输入才 16.9 MB），全是假阳性。

## 三、图形：用运行中的游戏当标准答案

**不要用启发式猜哪块是图形。** 第一版用「高熵 + 多索引」打分，挑出 2047 个
候选，渲染出来全是雪花——噪声恰好满足这两个条件，所以打分方向本身就是错的。

可靠的判据是让游戏自己说：

```
node games/sacred-stones/scripts/vram-oracle.mjs --frames 900
```

它引导卡带跑到标题画面，取 VRAM（96 KiB）里所有 32 字节图块的哈希，再回到
压缩块里逐 32 字节找同样的字节串。结果（`--frames 900`）：

- VRAM 里非纯色图块 **1,611** 个；
- **342** 个压缩块命中至少一个图块，累计命中 **2,588** 次；
- 前几名是"整块都命中"：`0x00B5F69C` 255/255、`0x00B60DDC` 254/254、
  `0x00B51E98` 248/248 —— 这几块就是标题画面用的图块数据，没有任何猜的成分。

### 4bpp 图块怎么读

- 每图块 32 字节 = 8 行 × 4 字节，一行 8 像素、每像素 4 bit；
- **低半字节是左边那个像素，高半字节才是右边**。写反的话画面会碎成斜纹
  （我第一版就是写反的，看起来像"解码错了"，其实只是像素错位）；
- 每个图块用哪个 16 色bank，由**图块地图条目**决定（每像素格的调色板号），
  不是全局固定的。所以单看一个块、固定用 bank 0 渲染，颜色必然不对——
  形状对、颜色错，就是"缺图块地图"的典型症状。

### 还没证实的

- Huffman 块在这份汉化镜像里的实际用途（解出 0 块，可能是我的树读取还没
  校准，也可能是它只用于音声/字库）；
- 图块地图的起始地址与尺寸字段的语义（要按 BGxCNT 逐帧读，别硬编码）；
- 字库：汉字大概率是位图字库 + 文本表，文本区是否压缩未验证。

## 四、可以复用的脚本

| 脚本 | 作用 |
| --- | --- |
| `scripts/dump-blocks.mjs` | 解出全部块并算特征，落 `.botharness/blocks/`（不进仓库） |
| `scripts/vram-oracle.mjs` | 用运行中的游戏筛出"确实是图形"的块 |
| `scripts/compare-block-lists.mjs` | 两份块清单求差集，带 ROM 闸门与畸形行分桶 |

`@gba-kit/gba-emulator` **只作参照物**：它不参与发布产物，`dist/` 里没有它。
