
### 2.1 入口分支

| 项 | 值 |
|---|---|
| 字节 @0x00 | `2e 00 00 ea` |
| 小端读入 | `0xEA00002E` |
| 指令 | ARM `B`（opcode 0xEA），24 位有符号立即数 `+0x2E` |
| 目标计算 | `PC + 8 + imm24*4`，此处 `PC=0x00000008` → `0x08 + 0x2E*4 = 0x08 + 0xB8 = 0xC0` |
| 跳转目标 | **`0x080000C0`** |
| 判定 | 标准 GBA ROM 入口，未被补丁破坏 |

### 2.2 各字段

| 偏移 | 字段 | 实测 | 说明 |
|---|---|---|---|
| 0x04–0x9F | Nintendo logo | 156 B | 首 4 字节 `24 FF AE 51`、末 4 字节 `21 D4 F8 07`，与标准值一致 |
| 0xA0–0xAB | title | `FIREEMBLEM8\0` | 日版 FE8 原值 |
| 0xAC–0xAF | game code | `BE8J` | **J = 日本版** |
| 0xB0–0xB1 | maker code | `01` | Nintendo |
| 0xB2 | fixed | `0x96` | 固定值，正确 |
| 0xB3 | main unit code | `0x00` | 正常 |
| 0xB4 | device type | `0x00` | 正常（非调试/从属设备） |
| 0xB5–0xBB | reserved | 7×`0x00` | 正常 |
| 0xBC | software version | `0x00` | |
| 0xBD | header complement | **`0xD7`** | 见 2.3 |
| 0xBE–0xBF | reserved | `00 00` | 正常 |

> logo 逐字节全等比对留给脚本（`fe8_scan.py` 内置参考表）。
> 本批只人工确认了首尾字节与长度，**不宣称已完成全 156 字节的逐字节比对**。

### 2.3 表头校验 —— 任务书的说法需要纠正

GBATEK 算法：`checksum = (-(0x19 + sum(ROM[0xA0..0xBC]))) & 0xFF`

```
title  "FIREEMBLEM8\0"  = 70+73+82+69+69+77+66+76+69+77+56+0 = 784
code   "BE8J"           = 66+69+56+74                           = 265
maker  "01"             = 48+49                                 =  97
fixed  0x96             =                                       = 150
0xB3..0xBC (10 字节)    全 0                                    =   0
                                                        sum     = 1296

computed = (-(1296 + 25)) & 0xFF = (-1321) & 0xFF
         = (-1321 mod 256) = 215 = 0xD7
stored   = 0xBD = 0xD7
```

**结论：表头校验通过（PASS），不是失败。**

任务书里"header checksum 不通过"与实测矛盾，已按实测记录。这有实际意义：

- 它说明**汉化补丁没有动 0x00–0xBF 这 192 字节**，头部完全是原版日版值；
- 所以任何"汉化改坏了头部"的推断都不成立，汉化的改动在别处（见第 4 节）。

## 3. 存档类型与容量（本批最高优先级）

### 3.1 扫描方法

GBA 备份库（backup library）会在 ROM 里留下一段可被识别为"存档芯片型号"的 ASCII 字符串，
形如 `<类型>_<电压标志>_V<版本>`。用 ripgrep 以二进制模式直接扫 `.gba` 文件。

> 这条路径能用的原因：`read` / `ops_read_files` 都拒绝非 UTF-8 的二进制，
> 但 `grep` 底层是 ripgrep，能对二进制文件命中并返回行号。

### 3.2 命中与未命中

| 签名 | 结果 |
|---|---|
| `EEPROM_V` | 无命中 |
| `SRAM_V` | 无命中 |
| **`SRAM_F_V`** | **命中 3 次**（行号 42044 / 60101 / 60331） |
| `FLASH_V` | 无命中 |
| `FLASH512_V` | 无命中 |
| `FLASH1M_V` | 无命中 |
| `SRAM_F_V103` | 命中 1 次（行号 42044） |
| `SRAM_F_V102` | 无命中 |

进一步收敛：`SRAM_F_V10[0-9]` 命中 1 次 → 精确字符串是 **`SRAM_F_V103`**。
`SRAM_F_V` 出现 3 次符合惯例：备份库同一份字符串在不同代码路径/库实例里会重复出现。

### 3.3 判定

| 项 | 结论 |
|---|---|
| 存档类型 | **SRAM** |
| 容量 | **256 Kbit = 32 KiB** |
| 定版字符串 | `SRAM_F_V103`（`F` = 仅 3.0V 电压的 SRAM 变体） |

判定依据（按 GBA 备份库语义，不需要反汇编）：

- 四种家族互斥：`SRAM_*` / `FLASH_*` / `FLASH512_*` / `FLASH1M_*` / `EEPROM_*`，各有独立字符串。
- 全文件**没有任何 FLASH 或 EEPROM 家族字符串**，所以排除 64 KiB FLASH、128 KiB FLASH1M、EEPROM。
- SRAM 在 GBA 上没有容量协商机制，该库只服务 256 Kbit，所以容量唯一。
- 3 次 `SRAM_F_V` 命中都指向同一型号，不存在混合声明。

**置信度：高。** 这一条不依赖任何反汇编或运行时观察，字符串本身就是权威声明。

### 3.4 缺口（诚实）

**3 处命中的精确字节偏移没拿到。** `grep` 只返回"文本行号"，
而文本行号是按 `\n` 切分的序号，**不能换算成字节偏移**。
换算需要 `data.find(b"SRAM_F_V103")`，即需要跑代码。
`fe8_scan.py` 的 `scan_backup_sigs()` 已经实现（含命中处的 24 字节 ASCII 上下文）。

**所以：类型和容量是定论，偏移是待补的细节。**

### 4.2 未取得：压缩流统计（阻塞）

第 3 问要求"合法流数量 / 解压尺寸直方图 / 前 20 代表偏移"，
必须先真的把每条流解压成功才能给数。

**这一步没做，原因是环境，不是方法**：

- 本机 DSH 的 `ops_bash` 与 `pwsh` 对**任何**命令（含 `echo hi`）都返回
  `exit code 3221225794` = `0xC0000142` = `STATUS_DLL_INIT_FAILED`，stdout/stderr 全空；
- 独立子 agent 复现同一现象（`python --version`、`echo shell-alive` 全部同一个码）；
- `app_launch` 直接调 python 两次 45s 超时；`run_in_background` 只是把失败延后；
- 对照：`rea` 能成功 spawn `cmd.exe`，说明 OS 能创建进程，**坏的是 DSH 的 shell 执行器**。

古登堡法则在这里适用：**我宁可交"没跑"，也不交"看着像真的假直方图"。**

脚本已按"跑一次就出全部数据"写好：`fe8_scan.py`（见第 6 节）。
它实现的是严格版语义：

- 4 字节头：byte0 低 4 位 = 类型（1=LZ77 / 2=Huffman / 3=RLE），byte1..3 = 24 位小端解压尺寸；
- **必须解压出恰好 `size` 字节**才算合法，否则返回 `None`；
- LZ77 的环形回指（`disp`）越界、RLE 的重复/原样块越界、Huffman 的树越界，一律立刻放弃，**不返回半截数据**；
- 除 `valid_streams` 外另记 `header_candidates`，把"长得像"和"真的解开了"分开，避免虚报。

### 4.3 待验证假设（不是结论）

| # | 假设 | 支持线索 | 怎么证伪/证实 |
|---|---|---|---|
| H1 | 汉化补丁没动头部，改动落在正文区 | 表头校验 PASS，title/game code/maker 全原版值 | 已基本证实 |
| H2 | `0x0ED000` 起的 364 KiB 高熵块是一整块压缩图形（或图形+字库） | 块熵 7.87–7.93 且连续，远超代码区 | 跑 `fe8_scan.py`，看该区 LZ77 合法流密度是否接近 100% |
| H3 | 中后段大低熵区（`0xBC4000` / `0xE47000` / `0xEFC000` 起）是未使用空间或极稀疏查找表 | 块熵 ≤1.0，大量块熵恰为 0 | 同 H2；零块如果落在流内部会被解压器直接判非法 |
| H4 | 镜像被扩到 16 MiB，真实内容约止于 `0xFE3800` | 尾部 114 KiB 全零，过渡块熵 3.26 → 6.21 → 4.10 → 0.36 → 0 | 已基本证实（零填充） |
| H5 | 汉化字库是重画的 1bpp/2bpp 字模，位置在文本区附近而非头部 | FE8 文本用自带字库 + 双字节映射；汉化必须替换字模 | 按"低熵 + 非压缩 + 定宽网格"特征定位候选，再用提取出的位图肉眼确认 |
| H6 | 文本区被重打包（插入双字节码 + 控制符），不是等长替换 | 中文比日文假名占位多，必然改变长度 | 只有在拿到干净 FE8J 原版做 diff 才能定论 |

> H5/H6 是本批**最需要人看**的两条：它们决定"文本能不能原样复刻"。

## 6. 诚实清单

本批**没有**做的事，以及为什么：

1. **LZ77 / Huffman / RLE 全扫描未执行** —— shell 无法创建进程（0xC0000142）。脚本就绪，数据为零。
2. **3 处 `SRAM_F_V103` 的字节偏移未取得** —— grep 只给行号，换算需要跑代码。
3. **Nintendo logo 未做 156 字节逐字节全等比对** —— 只人工核了首尾字节与长度；脚本已内置参考表待跑。
4. **没有反汇编、没有执行 ROM 代码** —— 按任务约束；因此第 4 节 H5/H6 无法定论。
5. **没有与干净 FE8J 原版做 diff** —— 手上没有原版，任务也明确不做字节 diff。
6. **输出目录没建出来** —— `games/sacred-stones/{docs,tools,extract}` 不存在，且本会话没有任何工具能创建目录
   （`write` 不建父目录，父目录缺失时报的是误导性的 `BotHarness Session file path cannot be resolved`）。

第 1、2、3 条都是"跑一次脚本就归零"的缺口，不是分析难题。

## 8. 能不能原样复刻（人最该看的一张表）

固定四列。**"能提"只代表字节能拿出来，不代表玩法能还原。**

| 项目 | 能否原样 | 差在哪 | 影响哪部分玩法 |
|---|---|---|---|
| 图形（LZ77 压缩图块） | **大概率能**（待验证） | 解压出图块 ≠ 还原画面：图块到屏幕还要靠拼装表 + OAM + 图块图索引，这些是代码行为；LZ77 合法流比例也还没实测 | 角色/单位头像、地图图块、UI 图标、战斗背景的观感 |
| 调色板与混合 | **色表能，混合不能** | 调色板是纯数据（15 位 BGR555）可直接取；但 alpha 混合、亮度渐隐是每帧写 `BLDCNT`/`BLDALPHA` 的代码，静态数据里没有 | 半透明窗口、暗角、天气/雾、淡入淡出转场 |
| 字库与文本 | **不能**（汉化已改） | 字库被重画成中文字模、文本改成双字节码并带换行/控制符；无干净原版无法 diff，编码表只能靠猜 | **全部对话、菜单、道具/技能名、战斗台词** —— 复刻的第一优先级 |
| 音频（MP2K） | **部分** | 音序与采样能提；但混音器参数（ADSR 包络、回声、主音量、声道分配）在代码里，音色还原只能靠调 | BGM、效果音、语音；**听感差异玩家最容易听出来** |
| 地图 / 瓦片 | **部分** | 瓦片图形可提；地图数据是压缩 tilemap + 事件表，事件脚本是字节码 | 关卡布局、地形、可走性、宝箱/村庄/增援点 |
| 战斗动画 | **不能** | 演出是脚本 + 精灵帧调度，帧序列与时序在代码/表里；只有图没有时序 = 幻灯片 | 战斗演出、必杀/闪避、暴击镜头 |
| RNG / AI / 时序 | **完全不能** | RNG 是 LCG 状态机、AI 是评分函数、时序靠中断；全在 ARM 代码里，纯数据面拿不到 | 命中率、升级成长、敌人行为、随机事件判定 |
| 存档 | **格式能** | SRAM 32 KiB、槽位结构可读出；但字段语义（单位索引/标志位）需反汇编；savestate 体积 = 32 KiB | 存档互通、继承、修改器/金手指 |
| 输入延迟 / 手感 | **完全不能** | 由中断优先级、帧同步、按键轮询时机决定，没有一条是数据 | 移动、光标、菜单响应速度；**这是"像不像"的关键** |

> 一句话：**能原样拿出来的是"素材"，拿不出来的是"行为"。**
> 复刻要还原的不是图像，是 CPU 每一帧做了什么。
