# 帧比对口径（frame compare）

## `self_sha256` 定义（写死，唯一解释）

`self_sha256 = sha256(文件字节，且把 `self_sha256` 字段的值替换成 64 个 ASCII '0')`

- 不是"排除该字段再算"（那会改变字节数），也不是"算完再填"（不收敛）。
- 校验方式：读文件 → 用正则把 `"self_sha256": "<64 hex>"` 的值替换成 64 个 `0` → 对整段字节做 sha256 → 与字段值比。
- 参考实现见 `tools/frame900-selfcheck.py`（若缺失，按上面三行实现即可）。

## 帧 900 合成（`extract/frame900/summary.json`）

- 输入：`extract/frame900.json`（同帧：DISPCNT / BGxCNT / BGxHOFS / BGxVOFS / BLDCNT / BLDALPHA / BLDY / VRAM / PALETTE，均为原始字节与寄存器值）。
- `bldcnt 0x0c42` → `firstTarget=[1]`、`mode=alpha`、`secondTarget=[2,3]`、`bd=false`、`eva=evb=8`（summary 里存字段，不存原始字）。
- 层：BG0 not-drawn（DISPCNT bit8=0）；BG1 first（274 tiles，14,564 不透明像素，1 色）；BG2 second（133 tiles，6,241 像素，78 色，11 个 palette bank）；BG3 second（255 tiles，38,400 像素，15 色，1 个 bank）。
- 混合在 **15-bit 域**做：`v = (A5*EVA + B5*EVB) >> 4`，逐通道，结果仍为 15-bit；PNG 再用 `v<<3|v>>2` 展开到 8 位。8 位域混合与 5 位域混合相差 1 个 5-bit 级，不能混用。

## A/B 判据（BG1 是否黑幕）

预测：BG1 色值全 0 且 EVA=EVB=8 ⇒ 被 BG1 覆盖且下方有 second-target 的像素，`out_with == out_without >> 1`（逐 5-bit 通道，floor）。

实测（`ab_test` 字段）：

```
diff_pixels = 13515
exact_half  = 13515   # 100% 命中预测
```

- 差为 13,515 而非 14,564：剩余 1,049 个 BG1 不透明像素下方 BG2/BG3 均透明，有无 BG1 都是背景黑，不产生差异、也不发生混合。
- 结论：BG1 在这一帧就是一层黑色遮罩，参与 alpha 混合；跳过它会让 14,564 个像素偏亮。

## BG1 的索引直方图（决定"黑"的来源）

`summary.json` → `layers.1.index_histogram`：15 个不同索引，全部落在 **bank 15**，且 `palette_raw` 全为 `0000`（前几个：idx13=1,685、idx2=1,604、idx11=1,500、idx8=1,338、idx12=1,308…）。

⇒ 不是"所有像素同一个索引"，而是 **bank 15 这一帧没被写入**（15 个索引映射到 15 个空槽）。这解释了两件事：

1. 视觉上是 1 色（全黑）；
2. 几何是真的（274 个图块被引用），**别的帧 bank 15 一旦被加载，BG1 会显出内容** —— 后续帧不能沿用"BG1 恒黑"的假设。

## BG2 的 78 色

4bpp 单 bank 上限 16 色，但 **map entry 的 bit12–15 逐图块选择 palette bank**：BG2 用了 banks 0–10（11 个），每 bank 最多 11 色，合计 78 色，属正常，不是 8bpp 误读、也不是字节当索引。

## 已知未覆盖（不得写成"全覆盖"）

- DARKEN 15-bit 域 vs @gba-kit 8-bit 域（约 13% 像素受影响）；
- `expand5` 展开方式（`v<<3` vs `v<<3|v>>2`）；
- Window / Mosaic / 仿射层；
- 模拟器内核 vs 真机。

## BG 寻址与掩码（帧 900 实测）

- 文本 BG 的屏幕尺寸取 `BGxCNT` bits14-15：`0`=256×256（32×32 tiles），`1`=512×512（64×64，按 `tileX>=32 / tileY>=32` 分四象限，各象限起始 0x800），`2`=256×512，`3`=512×256。
- 帧 900 `BG1 CNT=0x1C01` ⇒ **size=0，256×256，无象限问题**；坐标为 `tileX=((px+hofs)&0xFF)>>3`、`tileY=((py+vofs)&0xFF)>>3`（先 `&0xFF` 再 `>>3`）。
- 透明由 **像素索引==0** 决定，不是调色板值：BG1 的 bank 15 全 `0000` 是**不透明黑**。
- 不透明掩码已导出：`extract/frame900/bg1-mask.png`（白=索引!=0，14,564 px，`sha256 e05ab9517808f6695a899f143d8726790115c6c43ae17e7f233b7ef3b380c114`），供与 oracle 的掩码逐像素对撞。
- 混合分解（**实测，2026-10-30 修正**）：`14,564 = 13,515（混合后可见变化）+ 1,049（混合了但结果同值）`。帧 900 的 BG2 有 6,241 个不透明像素、BG3 有 38,400（**满屏**），所以 BG1 的 14,564 个像素**全部**都有第二目标，不存在"无第二目标"的像素；那 1,049 的共性是**下方首个第二目标颜色 = 0x0000**，黑混黑仍是黑。字段名已从 `no_under_pixels` 改为 `same_result_pixels`，并断言 `under_black_pixels == same_result_pixels == 1,049`。

## 盲区（black-on-black）与掩码对撞

`bg1-blindzone.png` 的白色 = **BG1 不透明且其下方首个第二目标颜色为 0x0000**（帧 900 为 1,049 px）。这类像素上"显示 BG1 的黑"与"不显示 BG1 的黑"完全同值，framebuffer 对撞**看不见**掩码对错：oracle 在盲区里是瞎的，**盲区里两边一致也不构成证明**。判定规则：掩码差异落在盲区外 ⇒ 真差异；落在盲区内 ⇒ 不作判决。

## 混合是逐像素条件，不是列表条件

混合发生的充要条件（在**该像素**上）：第一目标侧有不透明像素，且第二目标侧有不透明像素（或 BD 使背景色参与）。两者缺一，该像素不混合，第一目标原样显示。**不得**实现为"secondTarget 列表非空 ⇒ 混"——`0x0C42` 的第二目标是 BG2|BG3，列表非空，但在帧 900 的 1,049 个像素上这两层都透明。

`BLDCNT` 位映射（已用断言钉住，`render-frame.py:25-27`）：bit0-5 = BG0..BG5（第一目标），bit6-7 = 混合模式，bit8-13 = BG0..BG5（第二目标），**bit13 同时是"背景色 BD 参与第二目标"**。`0x0C42` ⇒ 第一目标 BG1、alpha、第二目标 BG2|BG3、BD 不参与。

## `self_sha256` 的边界

`self_sha256` 只能发现"字节被改过"，发现不了"被故意改过"（改完顺手重算即可）；它是自检，不是校验和基线，不得用于"证明某份产物未被改动"的句子。

## 寄存器快照必须比画面早一帧（lag-1，实测）

游戏在 **VBlank** 里写 `DISPCNT`/`BLDCNT`/`BGxCNT`/`BGxHOFS`。所以：

> 跑完第 N 帧后读到的寄存器，是给**第 N+1 帧**用的。

要让寄存器与"第 N 帧那张图"配得上，必须这么做：

```js
for (let i = 0; i < frames - 1; i += 1) gba.runFrame();
const snap = snapshotRegistersAndMemory();   // ← 快照第 N 帧渲染前
gba.runFrame();                              // ← 这一帧就是第 N 帧
const framebuffer = gba.ppu.getFramebuffer();
```

判据不是"我觉得这样对"，而是硬件的输出：

| 时序 | 帧 900 整屏合成结果 |
| --- | --- |
| 快照晚一帧（旧写法） | 差 7,456 像素（19.4%） |
| 快照早一帧（lag-1） | **`diffPixels: 0`** |

这个错误把一整轮的对外产物都带歪了：旧 `frame900.json` 的寄存器属于第 901 帧，
基于它算出的 `14,564 / 13,515 / 1,049` 三个数和三张掩码全部作废。

**给下游的规矩**：以帧 900 为输入的产物，必须带 `vram_sha256`（和 dump 的 sha），
旧数字就地标 retired，不许与新的混引。

## 混合相关三个数必须分开数（`blendStats`）

同一份快照上，这三个数含义不同，混用就会得出"差 941 像素"这种无主差值：

| 名字 | 帧 900 值 | 含义 |
| --- | --- | --- |
| `branch` (a) | 12,574 | 执行了混合分支的像素数 |
| `changed` (b) | 11,643 | 混合后结果 ≠ 第一目标原值 |
| `exactHalf` (c) | 931 | 结果恰等于 `(top + below) >> 1` |

`(a) − (b) = 931` 就是"混合分支跑了但结果没变"的那批，也就是**盲区**。

## 盲区必须由参照侧算

盲区若由被测实现的输出定义，它错在哪盲区就塌到哪——于是任何差异都能被"落在盲区里"解释掉。

正确做法：**同一份 savestate、同一帧，只把 `BLDCNT` 在真值和 `0` 之间切换**跑两次硬件，
输出相同的像素就是盲区。被测实现完全不参与。

帧 900 实测三条独立路径（我的计数 / 逆向的静态渲染器 / 硬件自身对撞）：

```
BG1 不透明 12,574    混合可见 11,643    盲区 931
```

三条路径在三个数上完全一致。交换对撞材料时只交换**计数 + 像素集合 sha + 直方图**，
不贴图；比"像素集合 sha"而不是 PNG 文件 sha——文件 sha 里混着编码器差异。

## 掩码/盲区对撞（1-bit 打包 sha）

- 约定：240×160 行优先；白=1、黑=0；每行 240 bit 按 **MSB-first** 打包，行末补 0 到整字节；sha256(全部行)。
- 我方（帧 900，dump `c1fdc400…` / vram `73025eda…`）：
  - `bg1-mask.png` 12,574 px，打包 sha `cb41549aedd4066d48c652cb7bd7d253856f88d28a398c382b62377d87282783`
  - `bg1-blindzone.png` 931 px，打包 sha `4df02f1ef466f1cb354c13db1f73ace945e46c1b48852786a216b88335c9a120`
- 与 游戏实现 侧 `games/sacred-stones/.botharness-mask/` 的两张图**逐像素相等**（打包 sha 相同）；PNG 文件 sha 不同只因编码器（我方 RGB、对方 RGBA/灰度），不构成差异。

## 硬件开关对撞（通用判据模板）

三段式，用于任何"我的实现 vs 参照"的判定：

1. **实现侧计数**：被测实现只报计数，不参与参照；
2. **独立静态渲染**：另一条代码路径重算同一量（本例：renders from dump）；
3. **改 IO 寄存器跑两次比输出**：同一 savestate、同一帧，只改一个寄存器（本例 `BLDCNT 0x0C42 ↔ 0`），两次输出相同的像素即"不可判区"。

只有第 3 步能排除"被测实现本身就是参照物"。适用面：BG2/BG3 混合、OBJ 层遮挡、Window 特效、任何"开了/关了某个硬件开关输出应当不同"的场景。

前提：抓帧时回读被改寄存器的实际值（否则游戏可能在 VBlank 改回，两次跑成同一配置）。掩码对撞统一用 1-bit 打包 sha（见上节），不等时输出对称差（像素数 + 前 20 坐标 + 每坐标两侧状态）。

### 约定事故记录：set_sha256 的 bit 序（2026-10-30）

同一组像素集合，两种打包得到两个不同的 sha：

| 产物 | MSB-first（本文件约定） | LSB-first（实现侧当前） |
| --- | --- | --- |
| bg1-mask (12,574 px) | `cb41549aedd4066d…` | `26a7999d49bd08c8…` |
| blindzone (931 px) | `4df02f1ef466f1cb…` | `99c0558d906caaeb…` |

集合本身已逐像素相等（`onlyMine 0 / onlyImpl 0`），差异**只在 bit 序**。以本文件的 MSB-first 为准；实现侧改一行后重贴即可。教训：sha 必须连约定一起传播，否则"相等"会被一个 bit 序判成"不等"。

### 已知答案向量（打包器自检）

手构 4×2 掩码（MSB-first、每行补 0 到整字节）：

```
row0: 1 0 0 1        → 0x90
row1: 0 1 1 0        → 0x60
bytes = 90 60
sha256 = 590ddde5444fee9ae8d200c7361b5f90927054c7b25a7524ef26acc28fb973c2
```

两侧打包器都必须产出 `0x90 0x60` 与该 sha；产不出即是 bit 序或补位规则不一致。
`bit_source` 语义钉死：**4bpp 图块索引 != 0（索引 0 透明）**，不是"白像素"，不是 alpha。

补充：2026-10-30 那次"两侧相同"实际是**同一个打包器算两侧的图**，只证明像素相同，不证明打包器一致；打包器一致性以本节向量为准。

## 掩码打包约定（判据的一部分，配已知答案向量）

`set_sha256` 只有在约定固定时才代表"像素集合相等"。本项目的真实事故：两侧逐像素比较
确认集合相等（`onlyMine 0 / onlyImpl 0`），但贴出来的 sha 有**四个不同的值**——
不是数据错，是两边各写了一份打包器，其中一份是 LSB-first。

约定（`src/extract/mask-pack.js` 的唯一实现）：

```
width 240 / height 160 / row-major / 白=1 / MSB-first / 行末补 0 到整字节 / 30 B 每行
摘要 = sha256(打包字节)，小写十六进制，不带前缀
```

**已知答案向量**（期望值由 Python `hashlib` 独立算出，不是跑实现再抄回来）：

| 向量 | 内容 | 打包字节 | sha256 |
| --- | --- | --- | --- |
| vec1 | 4×2，行 0 = `1011`、行 1 = `0100` | `b040` | `5ebc514a714b7e738505fabf839804b26e95d56d0ca54cf6b29052ebd8b9fe37` |
| vec2 | 240×1，仅第 239 像素为 1 | `00…0001`（30 B） | `65279e18ab3349670c5e4029a6c82a51ebb51969cb9ea6c486a5248bd50b3d6a` |

`mask_convention` 必须随每份掩码的 `summary.json` 走，六项齐全：
`{width, height, row_major, bit_source, msb_first, pad}`（外加 `bytes_per_row`）。
`bit_source` 要写清"这里的 1 代表什么"（`bg1-opaque` / `bg1-opaque-and-same-result`），
三者在本帧可能同集、换个帧就分家。

## dump 里两个摘要的复算规则

别人要能**独立复算**，规则必须公开：

- `registers_sha256 = sha256(UTF-8 的 JSON.stringify(registers))`，键序就是 dump 里 `registers` 对象的书写顺序，
  **不含任何空白字符**（不是 `JSON.stringify(x, null, 2)`）。
- `self_sha256 = sha256(文件字节，其中 self_sha256 的值替换成 64 个 '0')`。
  不用"删掉字段再序列化"：那依赖键序与缩进，换语言重算极易对不上，而一个对不上的自校验字段比没有更坏。

## 已作废的结论（不要再引用）

### `931` 这个数在修好前也出现过 ⇒ 那一轮不构成证据

- 事实：在把盲区实验改成"**每条扫描线渲染前强制写入 `BLDCNT`**"之前（当时是帧末回读 / 第 0 行取样，实际拿到的是**半帧对照**），`blindzone` 也得到 **931**。
- 因此：**修好前那一轮的 931 是蒙对，不能算交叉验证**。三条路径（我的计数 / 逆向静态渲染器 / 硬件开关对撞）在 931 上一致这件事，只有"逐扫描线强制写"之后的版本才算证据。
- 影响范围（重要，别放大）：**只有盲区这一路受影响**。`bg1Opaque = 12,574` 是"合成器里 BG1 索引 != 0"的计数，与 `BLDCNT` 采样点无关；`blendVisibleWhereBg1 = 11,643` 由掩码与混合可见性推出，也未被这一轮的采样错误污染。
- 更一般的规矩：**"两个数相等"必须先证明"两个数都是被正确产生的"**。取样点本身也是实验的一部分——帧末回读、首行取样、逐行强制写，三者给出三个不同的世界，而它们可能恰好给出同一个数字。

### 帧 3200 的「OBJ 1,105 像素差 / 硬件丢了精灵」

- 当时的假设是"GBA 每行最多 64 个精灵 / 1024 像素，超限的精灵被硬件丢弃"。
- 探针（同一 savestate、只切 `DISPCNT` 的 OBJ 位）实测：`128 个精灵 / 每行最大 228 像素 / 最忙一行 17 个精灵`，**两条上限从未接近**；我的 OBJ 像素与硬件逐行不一致 **0**。
- 那一帧的 1,105 差同样来自 lag-1 的时序错误（画面与另一帧的 OAM 拼在一起）。
- 现状：`renderObjLayer` 的 `maxSpritesPerLine` / `maxPixelsPerLine` **默认 `null`**，只有打开才会丢弃；打开必须先改测试里的那条"默认关闭"断言。

## 帧号守卫（把 lag-1 变成机械判定）

同一件事在一天里踩了三次：帧 900 整屏差 7,456 px、帧 3200 差 1,105 px、盲区 1,250。

三次都不是不细心，而是**流程里没有任何一处会因为帧号不对而失败**。而错帧产出的数字往往完全合理——
`1,250` 不比 `931` 更可疑，它甚至自洽地解释了"多出来的 319"。唯一能抓住它的东西就是"这帧编号不对"。

所以规则变成代码（`src/extract/frame-guard.js`）：

1. 任何测量输出必须带 `frameNo`；
2. 脚本对期望帧号断言，不一致**拒绝输出**（抛 `FRAME_MISMATCH`，不写结果文件）；
3. 复现别人的结果时先 diff `frameNo`，不一致直接拒，不许进入像素比较（命令行：`--expect-frame N`）。

## 采样器的交叉验证（A == C）

两种彼此独立的取样方式——"跑帧前写一次"（A）与"逐扫描线强制写"（C）——落在**同一个集合 sha
`4df02f1e…`、`onlyA 0 / onlyC 0`**。这不是"多了一条路"，而是给**采样与打包链路**做了一次对撞：
取样点、掩码生成、bit 打包三处任何一处错，集合 sha 都会不同。

两条结论都要，不许用一个省掉另一个：

- **逐扫描线那套是通用正确做法**（真有机型会中途改配置），发货口径就用它；
- 本帧 `A == C` 恰好是"这一帧没有中途改写"的**证据**（逐行实测 160 行全是 `0x0c42`、`changeCount 0`）。

## 产地章：两个锚，各记各的

```json
{ "format_version": 2,
  "source": { "commit": "8a1cc43…", "path": "tools/mask-pack/pack.mjs", "sha256": "…" },
  "copy":   { "commit": "bdbc40a…", "path": "games/sacred-stones/tools/mask-pack-reference.mjs", "sha256": "…" } }
```

- 源与副本分别停在**不同**的 commit 上，一个 commit 里取不到两份内容 ⇒ 扁平单锚**判失败**，不做兼容读取
  （只要 flat 还能过，就会有人一直用 flat，而"reader 支持双锚"让人误以为迁移完成了）。
- 判定**不读章里的 sha**：两侧各自 `git show <anchor.commit>:<anchor.path>` 重算后再比；
  章只回答它才能回答的问题——"这对内容自从登记以来，有没有人在没重刷的情况下动过"。
- 默认读 `HEAD`（看现在），`--as-recorded` 读章里的锚（看当时）。没有后者，"三天前那次为什么是绿的"就复算不出来。
- 章里**不放时间戳**：`refreshed_at` 会让"刷新成功"和"内容变化"绑死，于是每次刷新都制造一个脏文件，
  `git status` 的"脏"从此不再表示"内容变了"。要留时间就写进提交信息。
- 刷新器必须**幂等**：内容相同就不写盘，连时间戳都不碰（`wroteCopy/wroteProvenance` 全 false 才是常态）。
