# 帧比较契约（`scripts/compare-frame.mjs`）

一句话：**在拿到能分层的数字之前，"看起来像"不算判据。**

## 为什么要有这份契约

截图是人手给的，规格不是。规格不定死，第一轮 diff 出来的东西会同时包含
"调色板错 / 图块地图偏移 / 行序错 / VRAM 残留 / 对象层没画"五类问题，
而它们看起来是同一件事：一片红。**红在哪一层不知道，就等于没有结论。**

## 三条硬规则

### 1. 一律先缩到原生 240×160，只用最近邻

模拟器截图常见 3x/4x 放大。放大图必须用**最近邻整数倍**还原：

```js
const sx = width / 240;
if (width % 240 !== 0 || height % 160 !== 0) throw new Error('不是整数倍');
if (sx !== height / 160) throw new Error('横纵缩放比不一致，图被拉伸过');
```

**绝不能用双线性**。双线性会把每个像素都改一点点，38,400 个像素全部进入
"有差异"，占比 100%，而它长得像"合成器完全错了"——实际上只是采样方式不同。
非整数倍直接抛错，不做"尽力而为"的缩放：用最近邻缩非整数倍得到的图不是任何
真实渲染，拿它比较得出的结论是噪声。

### 2. 逐通道容差默认 1

`BGR555 → RGBA8` 至少有两种常见换算：

- `(v << 3) | (v >> 2)`——把 5 位线性拉伸到 8 位
- `Math.round(v * 255 / 31)`——按比例取整

同一个 5 位值 `v`，两者会差 1。所以**全通道严格相等只适用于"两张图出自同一段
转换代码"**。跨实现比较时容差取 1，并且 `maxChannelDelta` 仍然如实输出——
容差是为了吸收表示差异，不是为了掩盖系统性偏移（系统性偏移会是几十）。

### 3. 输出三个数 + 一个分层入口

```
差异像素 256 / 38400 = 0.667%
最大单通道偏差 200（容差 1）
区域 {"x":64,"y":32,"width":16,"height":16}
首个差异点 {"x":64,"y":32,"actual":[200,0,0,255],"expected":[0,0,0,255]}
```

只给"看起来差一点"等于没有判据。`--json` 落盘同一份结构，便于进 CI。

## 分层顺序：单块 → 一块区域 → 整屏

1. **单块**：一个已知位置的 16×16 图块，像素相等 → 证明调色板、半字节顺序、
   bank 选择都对；
2. **一块矩形区域**（`--region x,y,w,h`）：证明图块地图的行列映射对；
3. **整屏**：这时才允许看全图，剩下的差异才是"地图没还原"或"对象层没画"。

跳级比较的代价很具体：本项目已经吃过一次同类亏——地址写错时 `decompress`
返回 `null`，而 `null` 的语义是"这块解不出来"，于是报错把人指到一个不存在的
解码器 bug 上。**错误和错误长得一样，是因为没有分层。**

## 用法

```bash
node scripts/compare-frame.mjs \
  --actual shot.png --expected composed.png \
  --native 240x160 --tolerance 1 \
  --region 64,32,16,16 --json region-1.json
```

退出码：`0` 无差异；`1` 有差异（数字在 stdout）；`2` 参数错误。

## 手写 PNG 解码器的交叉校验（一次性，已通过）

`src/extract/png.js` 是零依赖手写实现。它的风险很特别：**如果它错了，期望图和
截图会一起错，`compare-frame` 会报 0 差异——满分通过，结论完全错。**

所以做了一次用外来实现（Python + Pillow）对同一批 PNG 的逐字节比对：

| 样本 | 说明 | 结果 |
| --- | --- | --- |
| `filter0..4 -rgb.png` | 240×160，行滤波 0/1/2/3/4（Sub/Up/Average/Paeth 全覆盖） | RGBA 摘要 `1810f3047841cc2b`，两边一致 |
| `filter0..4 -rgba.png` | 同上但带 alpha（含全透明区与 128 半透明区） | RGBA 摘要 `1af6cd1051c8da2b`，两边一致 |
| `pil-rgb.png` / `pil-rgba.png` | Pillow 自身写出的 PNG | 与上表同值，一致 |
| `pil-paletted.png` | color type 3（索引色） | 按设计拒绝，并打出 IHDR 字段与可执行建议 |

样本与脚本留在 `.botharness/png-crosscheck/`（不进仓库、不进运行时依赖）。
**判据一句话：写解码器的人和验证解码器的人，不能是同一次判断。**

遇到不支持的格式时报错长这样，为的是一次沟通解决，而不是"请重截"三轮：

```
不支持的 PNG：只支持 RGB/RGBA
  IHDR: width=240 height=160 bitDepth=8 colorType=3(索引色(paletted)) interlace=0
  → 请导出为 24 位 RGB 或 32 位 RGBA、非隔行（索引色请先转成 RGB）
```

## 期望图从哪来（这是硬要求）
期望图**必须**由「帧 900 的 VRAM 图块 + 帧 900 的 BG 调色板 + 图块地图」三者合成，
且图块与调色板都固定在夹具里：

- 图块哈希：`test/fixtures/vram-title-tiles.json` 的 `tiles`（1,611 个）
- BG 调色板：同文件的 `bgPalette`（512 字节原始值 + sha256
  `dfa203d7e75e3051933b21914e6a2194d8b20178cea4860d3d624df46e1b4c2e`）

**不许从 ROM 里另找调色板，不许猜 bank**。判据是「用这一帧的调色板还原这一帧的
图块」；换个调色板即使颜色好看，也是对不上原画面的。
