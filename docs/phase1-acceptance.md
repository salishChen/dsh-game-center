## 0. 证据分栏与验收纪律（硬约束）

本验收矩阵延续项目经理与用户确定的严格取证标准，每个验收项必须在下列**唯一一栏**打勾，不得混填、不得泛化：

| 分栏 | 含义 | 阶段1 是否计入通过 | 说明 |
| --- | --- | --- | --- |
| `STATIC` | 静态代码分析、类型守卫、配置审查 | 否 | 仅作设计与契约依据 |
| `UNIT` | 进程内单测（纯函数/状态机/规则引擎） | 否 | 逻辑正确性验证 |
| `MOCK` | 模拟桩（Fixture、Stub、Mock Bridge） | 否 | 契约接口联调验证，不得冒充真实 DSH |
| `BUILD` | 编译打包与产物生成（tsc、esbuild） | 否 | 构建通过不等于功能正确 |
| `DSH-REAL` | 在真实运行的 DSH 环境中实操观测并留证 | **是** | 唯一可关闭最终验收门禁的证据级别 |
| `AUTH-PENDING` | 需用户单独授权的操作（付费模型调用/远程发布） | 否 | 保持挂账，绝不擅自执行 |

**验收硬纪律**：
1. **独立判定**：QA 独立于实现者给出验收结论，无确凿测试日志/截图/截获数据等证据不得报通过；
2. **严防假阳性**：严禁在断言中使用宽泛默认值（如 `?? 0`、`|| true`），异常必须显式暴露；
3. **禁止擅自修改在线产物**：当前平台根目录通过 junction 挂载在运行中 DSH profile，禁止直接修改或重新构建 `lib/`、`dist/`，所有中间产物严格隔离在 `staging/`；
4. **禁止未授权操作**：不自动刷新/重启 GUI、不调用付费模型、不推送 GitHub/Gitee 远程仓库。

## 2. 阶段1 核心验收矩阵（12 项关键验收场景）

### 2.1 目录与审批安全（Catalog & Approval，对应计划 A1、A2）

#### 【M1-01 / A1】GitHub Issue 机器块解析及异常防御
- **目标**：严格从 GitHub Issue 正文提取唯一 `gamecenter-json` 机器块，过滤异常输入；
- **对应计划**：`A1` Issue 机器块解析
- **验收用例**：
  1. 正例：标准 Issue 正文提取符合 Schema 的单条机器块（PASS）；
  2. 负例-多块：正文中包含 2 个及以上 `gamecenter-json` 机器块，必须拒绝并报 `PROTOCOL_INVALID`；
  3. 负例-损坏：JSON 语法错误、非对象结构、缺失必须字段，必须拒绝；
  4. 负例-超限：Issue 正文超过安全限制（如 > 64KB）或字段超长，直接丢弃拒绝；
  5. 负例-未知版本：`schemaVersion` 不是支持的主版本（当前仅支持 1），显式报错拒绝。
- **证据级别要求**：`UNIT`（纯函数解析测试）

#### 【M1-02 / A2】审批五元组防篡改判定
- **目标**：安装前严格校验审批记录与 Issue 发布元组，必须逐字段一致；
- **对应计划**：`A2` 审批五元组比对
- **五元组字段**：`{ gameId, repository, commit, manifestDigest, bundleDigest }`
- **验收用例**：
  1. 正例：五元组与受保护审批记录逐字完全匹配，判定允许安装；
  2. 负例-仓库篡改：`repository` 被篡改为第三方仓库（即使 commit 与摘要完全相同），坚决拒绝；
  3. 负例-代码篡改：`commit` 发生变动，坚决拒绝；
  4. 负例-内容篡改：`manifestDigest` 或 `bundleDigest` 发生哈希变动，坚决拒绝；
  5. 负例-无审批记录：Issue 存在但审批库无对应记录，判定未获审批，不可安装；
  6. 负例-短哈希伪造：`commit` 非 40 位小写十六进制、摘要非 64 位 SHA256，直接拒绝。
- **证据级别要求**：`UNIT`（包含五项单独篡改负例断言）

### 2.2 固定提交安全安装与沙箱隔离（Secure Installation & Isolation，对应计划 A3、A4）

#### 【M1-03 / A3】固定提交拉取与哈希强校验
- **目标**：仅允许按 40 位完整 commit 下载源码/产物，安装前完成摘要比对；
- **对应计划**：`A3` 固定提交安装
- **验收用例**：
  1. 正例：下载产物后，实测计算出的 `manifest.json` 与 `dist/` 产物哈希与审批记录完全一致，安装进入下一阶段；
  2. 负例-摘要不符：故意篡改下载包内一个字节，校验失败，立即终止安装并彻底清理临时解压目录；
  3. 负例-禁止浮动分支：禁止按 `main`、`HEAD` 或标签（tag）作为安装信任依据，必须锁定至不变的 commit SHA。
- **证据级别要求**：`UNIT` + `MOCK`

#### 【M1-04 / A3】路径逃逸与目录遍历防御（Path Traversal / ZipSlip）
- **目标**：严禁解压或安装过程中越权向游戏受限目录外写入任何文件；
- **对应计划**：`A3` 路径安全
- **安装根限制**：严格受限于 `<LIBRARY_DIR>/<gameId>/<commit>/`；
- **验收用例**：
  1. 负例-相对路径穿越：压缩包内或 manifest 中包含 `../../etc/passwd`、`../evil.js`，安装器必须抛错并拦截；
  2. 负例-绝对路径与盘符：包含 `C:\Windows\...` 或 `/usr/local/...`，必须拦截；
  3. 负例-恶意符号链接：包含指向安装目录外部的 symlink/junction，解包器严格拒绝并判定非法；
  4. 负例-特殊系统名：包含 Windows 特殊设备名（`CON`, `PRN`, `AUX`, `NUL`, `COM1`）或 NTFS 备用数据流（`file::$DATA`），严格拒绝。
- **证据级别要求**：`UNIT`（覆盖针对恶意构造归档的拒绝测试）

#### 【M1-05 / A4】版本隔离与无破坏共存
- **目标**：同游戏的不同 commit 版本完全物理隔离，不互相覆盖；
- **对应计划**：`A4` 隔离安装不覆盖旧版本
- **验收用例**：
  1. 正例：先后安装 `game-A@commit1` 与 `game-A@commit2`，两者目录独立并存；
  2. 正例：旧版本运行时其目录被只读锁定，新版本安装不干扰旧版本运行，旧版本存档保持独立。
- **证据级别要求**：`UNIT` + `MOCK`

#### 【M1-06 / A3】零脚本执行保障
- **目标**：安装过程仅为受控解包与静态验证，绝对不执行不可信代码；
- **对应计划**：`A3` 清单与执行安全
- **验收用例**：
  1. 静态断言：安装逻辑中严禁调用 `child_process.exec`、`npm install`、`pnpm install` 或触发 `postinstall` 脚本；
  2. 产物要求：游戏产物必须由开发者预编译为纯净静态 `dist/`，平台不承担在线编译与脚本构建。
- **证据级别要求**：`STATIC` + `UNIT`

### 2.3 扫雷首款玩法与 AI 局生成契约（Minesweeper & AI Generation，对应计划 A7、A8）

#### 【M1-07 / A7】扫雷确定性规则引擎
- **目标**：游戏局内逻辑完全由本地程序确定性执行，不依赖 AI 也不允许 AI 篡改规则；
- **对应计划**：`A7` 扫雷规则引擎
- **验收用例**：
  1. 规则正例：翻开数字格、空白格连锁自动扩散展开、插旗标记/取消标记逻辑正确；
  2. 首击保护：玩家点击的第一格绝对不能是雷；若初始雷位与首击重合，引擎必须确定性移雷或重新置换；
  3. 胜负收敛：触雷立即触发失败（`defeat`）；所有非雷格全部翻开立即触发胜利（`victory`）；
  4. 种子复现：给定相同种子（seed）时，棋盘雷位与布局完全确定且可复现。
- **证据级别要求**：`UNIT`（在扫雷游戏单测与契约测试中完全通过）

#### 【M1-08 / A8】AI 局生成契约与作弊防御
- **目标**：AI 仅作为“发牌员/出题人”生成开局棋盘，严禁参与局内判定；
- **对应计划**：`A8` AI 生成棋盘校验
- **验收用例**：
  1. 格式契约：AI 生成结果必须严格匹配 `MinesweeperBoardV1` Schema（宽、高、雷数、雷坐标列表）；
  2. 合规校验：生成的雷数必须精确等于设定参数，坐标必须在宽高范围内且不得重复；
  3. 作弊防御：游戏进行中的每一次点击，由规则引擎独立比对内部雷图，绝不把完整雷位透传给玩家客户端未翻开区域，亦不调用 AI 进行局内判定；
  4. 阶段1 模型边界：阶段1采用离线确定性 Fixture 生成器（`MOCK`），不发起真实付费模型调用。
- **证据级别要求**：`UNIT` + `MOCK`

### 2.4 跨存档与主 API 越权防御（Sandbox & Security Boundaries，对应计划 A9）

#### 【M1-09 / A9】游戏运行时隔离与 Bridge 越权拦截
- **目标**：游戏运行在受限沙箱（如 iframe/Worker），只能通过 SDK 调用白名单能力；
- **对应计划**：`A9` 游戏越权防御
- **验收用例**：
  1. 凭据隔离：游戏内代码无法读取到 DSH 平台的 `runtimeToken` 摘要、API Key 或 Session Token；
  2. 跨存档越权：游戏 A 试图读取或覆盖游戏 B 的存档 ID（`saveId`），Bridge 坚决拒绝并返回 `SECURITY_DENIED`；
  3. 未暴露接口越权：游戏试图直接调用未在白名单的 Host RPC 方法（如操作系统指令、文件删除、通用模型调用），Bridge 严格拦截；
  4. 消息源拦截：非本游戏 iframe 发来的 `postMessage` 信封，直接丢弃不予响应。
- **证据级别要求**：`UNIT` + `MOCK`

### 2.5 存档持久化、事务与关闭恢复（Save Persistence, Transaction & Resume，对应计划 A5、A6）

#### 【M1-10 / A5】Host 事务性存档与 Revision 单调性（原子 Checkpoint 强约束）
- **目标**：基于真实 SQLite 后端建立原子事务，彻底杜绝并发覆盖、进程重启回退与重试重复自增；
- **对应计划**：`A5` 存档事务与旧代次拒写
- **原子事务与并发模型约束（PM 强约束）**：
  1. **同连接 BEGIN IMMEDIATE 事务**：同一事务内完整闭环 `SELECT` 校验已有记录 → `operationId` 幂等与内容一致性判定 → `expectedRevision` 冲突判定 → `UPSERT` 写入新 revision 与 operation_id → `COMMIT`，任何失败立即 `ROLLBACK`；
  2. **跨进程竞争强互斥**：子进程 A 与子进程 B 指向同一 SQLite DB 文件、携带相同 `expectedRevision` 并发保存，必须且仅有一个提交成功（revision 推进），另一个必须明确被拒绝（`STALE_RUNTIME` 或冲突拒绝）；严禁用单进程内两个对象实例伪造跨进程验证；
  3. **Operation 幂等与内容防护**：相同 `operationId` 重新提交，若内容一致必须幂等返回原 revision（绝不重复 +1）；若相同 `operationId` 提交不同内容，坚决拒绝；
  4. **跨重启 Revision 库内对账**：进程退出重开后，新实例必须先读底层持久库提取已有最大 revision，新写入必须在此基准上单调自增（2→3），严禁内存丢失导致 revision 回退到 1；
  5. **事务中断回滚与损坏拒读**：写入过程中断或发生异常，底层事务必须原子回滚保留旧版本；若数据库中存档内容被篡改，读取时完整性摘要校验必须报错拒绝。
- **证据级别要求**：`UNIT`（含真实 OS 子进程并发竞争与 SQLite 事务测试）

#### 【M1-11 / A6】暂停超时回落与保全
- **目标**：当弹层请求关闭时，若游戏未能及时确认，平台必须超时收敛；
- **对应计划**：`A6` 暂停超时控制
- **验收用例**：
  1. 正常暂停：发出 `requestPause` 后，游戏在预算内（如 3000ms）响应 `saveAck`，状态收敛至 `paused`；
  2. 超时回落：故意让游戏挂起不响应，超过 `PAUSE_TIMEOUT_MS`（3000ms）后，Host 自动回退至最近一个有效检查点，状态置为 `recovery-available`，绝不无限挂起阻塞弹层关闭。
- **证据级别要求**：`UNIT`

#### 【M1-12 / A6】关闭重开恢复同进度一致性（端到端核心目标）
- **目标**：验证“关闭即暂停、重开同进度”的用户体验闭环；
- **对应计划**：`A6` 端到端关闭恢复
- **验收用例**：
  1. 启动扫雷游戏，翻开 3 个格子，插 1 面旗，计时走过 15 秒；
  2. 触发弹层关闭（Escape 或关闭按钮），系统执行 `requestPause` 并持久化当前检查点；
  3. 彻底销毁当前游戏实例与上下文；
  4. 重新打开游戏中心，选择该游戏继续；
  5. **恢复一致性断言**：

     - 计时进度精确恢复；
